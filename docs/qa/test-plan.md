# 第一版測試計畫（Test Plan V1）

對應規格：#1；票：#3–#12。原則：只測外部行為，驗收條件都要能實際驗證（見 #1「測試決策」）。

## 1. 測試層級與接縫

| 層級 | 範圍 | 工具 |
|---|---|---|
| 單元／規則測試 | 投票計分、排除、替代、排名、備選清單（純函式） | Dart `test` |
| 接縫一：Trip repository | 建立旅程、加入、投票、發送定位、結束旅程 | Firestore 模擬器 |
| 安全規則測試 | 非成員、旅程結束後的讀取權限 | `@firebase/rules-unit-testing` |
| 接縫二：排路線函式 | 輸入候選景點、交通時間矩陣、營業時間、每日時數，驗證輸出 | Cloud Functions 單元測試，Google API 一律用假資料 |
| Widget／整合測試 | 地圖標記、聚合、舊位置樣式、提示 | Flutter `integration_test` |
| 實機與實地測試 | 推播、省電模式、台日美戶外定位與路線 | 實機清單見第 4 節 |

每張票合併前：該票的自動化測試通過、CI 綠燈，且該票的離線案例通過。

## 2. 各票測試案例

### #3 專案骨架、旅程基礎、離線快取
| ID | 情境 | 預期 |
|---|---|---|
| T3-1 | 登入後建立旅程 | 產生旅程與邀請 |
| T3-2 | 另一使用者用邀請加入 | 成為成員，看得到旅程 |
| T3-3 | 非成員直接讀取旅程文件 | 安全規則拒絕 |
| T3-4 | 使用過期或無效的邀請 | 無法加入，有明確提示 |
| T3-5 | 斷網後開啟已載入的旅程 | 資料可讀 |
| T3-6 | 斷網時修改資料，恢復連線 | 同步成功，兩台裝置一致 |

### #4 提議景點與投票
| ID | 情境 | 預期 |
|---|---|---|
| T4-1 | 同一成員對同一景點連投兩次不同選項 | 只留最後一票，總分正確 |
| T4-2 | A 投票，B 的畫面 | 5 秒內看到總分更新 |
| T4-3 | 2 人旅程投「不想去」 | 立即計 −1，出現可略過的替代景點提示 |
| T4-4 | 略過提示 | 票仍有效，景點顯示「待提出替代方案」 |
| T4-5 | 提出替代景點 | 所有成員都能對它投票 |
| T4-6 | 4 人以上旅程投「不想去」 | 不出現替代景點提示 |
| T4-7 | 離線投票與提議，恢復連線 | 同步，不重複、不遺失 |

### #5 排名、排除、替代判定、備選清單（邊界值重點）
「不想去」人數須**嚴格大於**成員數 × 3/4 才排除：

| ID | 成員數 | 不想去人數 | 預期 |
|---|---|---|---|
| T5-1 | 4 | 3 | 不排除 |
| T5-2 | 4 | 4 | 排除 |
| T5-3 | 5 | 3 | 不排除（3 < 3.75） |
| T5-4 | 5 | 4 | 排除 |
| T5-5 | 8 | 6 | 不排除（6 = 6，未嚴格大於） |
| T5-6 | 8 | 7 | 排除 |
| T5-7 | 8 人但只有 4 人投票，其中 4 人不想去 | 不排除（以全團人數計） |
| T5-8 | 3 | 3 | 不排除（小團不排除） |

| ID | 情境 | 預期 |
|---|---|---|
| T5-9 | 小團替代景點總分 +1 | 取代原景點 |
| T5-10 | 小團替代景點總分 0 | 原景點保留 |
| T5-11 | 小團替代景點總分 −1 | 原景點保留 |
| T5-12 | 小團從未提出替代景點 | 原景點保留，依總分排名 |
| T5-13 | 兩景點同分，想去票數不同 | 想去多者在前 |
| T5-14 | 同分且想去票數相同 | 不想去少者在前 |
| T5-15 | 某天有 7 個候選景點 | 排 5 個，2 個進備選清單，沒有任何景點被刪除 |

## 3. 隱私與權限必測（跨票）
- 非成員讀不到旅程、投票、位置（#3、#10）。
- App 不申請背景定位（#8）。
- 旅程結束後位置完全不可見，包括伺服器與本機快取（#10）。

## 4. 實機與實地測試
- 品牌與省電模式：小米、OPPO、三星，各開啟省電模式測推播送達（#12）。
- Android 版本：至少涵蓋三個主要版本（實際版本待依目標使用者定案）。
- 實地：台灣、日本、美國戶外各測定位準確度與回程路線（#8、#11）。

## 5. 規格尚未說清楚、需要確認的地方
1. **#9 最近發送者同時發送**：兩人發送時間相同時，顯示誰的頭像？
2. **#5 小團的替代景點本身被投「不想去」**：是否也要再提出替代景點，還是只計分？
3. **#12 手機時間不準時**：以修改時間為準，但手機時間可能被調錯，要怎麼校正？
4. **#10 是否在起飛前提早結束**：目前依起飛時間結束，等使用者決定。

已定案（2026/10/26）：旅程依回程起飛時間自動結束，沒填就在結束日 23:59 結束，建立者也可提早手動結束；離線衝突以修改時間最晚的為準，被覆蓋的版本保留在修改紀錄；一天滿 5 個景點時要先換出一個。
