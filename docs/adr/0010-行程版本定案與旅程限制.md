# 0010 行程版本、定案與旅程限制
- 狀態：已採納（2026-10-27）｜關聯：0004、0007、0009、#7、#25
## 背景
2026-10-27 的設計文件新增了行程版本、定案、復原、旅程天數上限和 1 人旅程等規則，使用者已經同意。
## 決策
1. **儲存版本**：「儲存」會把整份行程存成一個版本，存在 `trips/{tripId}/versions/{versionId}`，欄位有 `number`（第 N 版，由伺服器遞增）、`name`（選填，最多 20 字）、`createdBy`、`createdAt`（伺服器時間），以及當下各天的 `stops`、`backupStops`。版本建立後不能修改，任何隊員都能儲存。
2. **定案**：旅程文件的 `finalVersionId` 指向唯一的定案版本，只有正副隊長能寫入，由權限規則擋住其他人。儲存和定案都會發一則聊天室系統通知，並寫進修改紀錄。
3. **和 0004 的關係**：各天的 `itinerary/{dayId}` 仍是即時的工作稿，衝突照 0004 以最晚儲存時間為準，修改紀錄由伺服器寫入（#25）。版本是工作稿的快照，不參與衝突判斷。還原舊版本只會把內容寫回工作稿，變成「未儲存的變更」，不會自動產生新版本。
4. **復原**：移到備選、從備選加入、與備選交換、依投票重排、還原版本、取消收藏，在 6 秒內可以復原。復原就是再寫一次反向的修改，照一般寫入處理，也會進修改紀錄。「同意或拒絕申請」不提供復原，改成按下前先確認一次，因為同意後伺服器會改動回程資料並通知所有人。封鎖成員也不提供復原。
5. **旅程天數上限**：結束日期減出發日期最多 30 天，建立和修改時都由權限規則檢查。
6. **1 人旅程**：只有隊長一人時，隊長退出就刪除整個旅程，由 Cloud Function 一併刪除子集合。
## 理由
版本和工作稿分開，離線衝突的規則就不用改。定案只限正副隊長，和 0007 的權限一致。申請被同意後的影響已經擴散出去，事前確認比事後復原可靠。
## 後果／取捨
多了 `versions` 子集合，以及 `finalVersionId` 的權限規則。#7 的行程編輯要一起做復原和版本畫面。設定為 30 天上限後，比較長的旅程要拆成兩趟。
